## Versioned owner detailed settings

`GET` / `PUT /api/matchmaking/detailed-settings` reuse the existing verified actor
transport and parser/no-store boundary. Actor IDs, masters, effective policy,
availability/location/downtime fields and all unsupported legacy keys are rejected
from the complete strict write envelope:

```json
{
  "expectedRevision": 0,
  "settings": {
    "messages": false,
    "plans": false,
    "matches": false,
    "friendsDiscovery": false,
    "datingDiscovery": false
  }
}
```

All five new defaults are OFF, including Dating. A virtual revision-zero read
does not insert a row and cannot contain default-on detailed choices. First
explicit write inserts revision one; established writes compare expectedRevision
atomically. Safe-integer revision exhaustion rejects rather than wrapping. No
backfill copies legacy or UI preview defaults into new consent. No new keys are
added to `AccountSettingsSchema`, `get_account` or `save_account` documents.

Read/save response: `{revision,settings,masters,effective}`. `settings` is the exact
stored choice. `masters` is read-only `{notifications,discoverable}` or null when
the actual `account_settings.settings` row is missing/malformed. The entire legacy
four-boolean shape is validated; unknown is not a guessed true or a claimed global
off value. The getter reads that persisted table directly, NOT `get_account`'s
defaulted document. Both sources are read in one SQL statement snapshot.

`effective` is **preference masking only**:

- Notifications master true AND each message/plan/match choice.
- Discovery master true AND each Friends/Dating choice.
- Unknown/off master suppresses all corresponding effective flags.

It is NOT a delivery receipt, device/channel permission, eligibility result, active
queue enrollment or verified live discovery. An explicitly saved Dating choice
does not activate real Dating, which remains the disclosed prototype. Identity,
reciprocal targets, adult eligibility, blocks and operational consent remain
separate requirements. No notification is generated by saving these booleans.

Master changes do not overwrite raw detailed choices or their revision. Detailed
saves never write legacy settings/preferences/chapters/profile or touch a queue.
Masters can legitimately change while detailed choices save; the response reports
its observed snapshot, not a CAS of the legacy domain. Actual discovery/delivery
consumers must reevaluate current masters at operation time, not reuse stale masks.
Legacy `availability`/`location` and downtime active-priority/no-resume semantics
are unchanged. Existing legacy whole-account stale-write risks are not fixed by
this separate resource; it prevents those writers from erasing detailed choices.

SQLSTATE `DS409` maps to Express `409/conflict` by upstream error body, not suffix
magic. Auth 401; validation 400; absent RPC/schema/permission/isolation dependency
503; provider/uncertain 503; malformed/readback mismatch 502. Revision and all
submitted choices must match readback; wrong effective masks also fail validation.
Malformed/uncertain PUT results are not “nothing saved” and must be reconciled by
GET, never blindly resubmitted. The actor SDK client uses a public key/user JWT;
no service-role actor writer or request-controlled RPC names are introduced.

### Independent product source review and concrete repairs

1. **Pre-passive-cleanup retained callbacks:** the hook previously fenced only with
   refs updated in passive effects. A descendant layout effect could invoke an
   old-session save/read before cleanup, or a retained ready save could bypass a
   new account-busy render. The hook now checks the current render's client binding
   at request entry and continuation, checks account-busy at mutation entry, and
   withholds write capability while the client binding/account writer is unsettled.
   Account busy changes do not abort an already-issued detail write; it still needs
   its authoritative readback or uncertainty reconciliation. Regression source
   invokes retained callbacks from layout effects during token/owner/busy transitions
   and rejects old-token reload transport.
2. **Lost round-trip master invalidation:** the old effect compared only the final
   master fingerprint to its last observed/attempted fingerprint. Off -> on while
